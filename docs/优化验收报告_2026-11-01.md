### 持久化失败与兼容边界

1. replay 不清日志。全部应用成功、快照可靠发布后才清除对应日志；应用、快照或日志清理失败均保留依据并上抛。
2. WAL 序列号和快照水位避免“快照已提交、清理前退出”后重复覆盖更新状态。JSON 先写唯一代次向量文件，再原子发布引用该代次的清单；加载检查代次。
3. 已发生内存变更但事务提交失败时，阻止后续写入与保存，要求重新创建/加载引擎；不把未确认状态保存成成功快照。它不是事务回滚机制。
4. fsync 成功追加才确认；grouped 保留异步缓冲语义，`engine.wal.flush()` 或成功保存才构成显式持久化确认。`close()` 是尽力清理，不能替代需要报错的 flush。
5. 新程序兼容旧快照与旧日志，但旧日志没有记录的原始时间无法补算。旧程序不支持新版事务日志，不能携带待重放的新日志直接降级；跨版本迁移先保留独立备份。
6. 未传 ns 仍是全库视图；ns 是调用方指定的检索范围，不是身份认证。QA 多会话接入应明确传 conversation_id。独立旧备份不在当前删除范围内。

## 4. 效果候选的采用与拒绝

### R1：已确认链的排序采用，自动匹配仍未验收

- 查询当前状态时，同作用域内已确认后继版本优先于祖先；放在可选 reranker 之后、最终截断之前。明确历史措辞或 `include_history=True` 保留历史排序。保留历史内容，不创建猜测的版本关系。
- 3 个对象互不重叠的种子，各 20 条已确认版本链，配套不同属性/用户等 240 条控制事实；当前版排序和历史保留通过。**这是确认链的排序测试，不是自动纠错匹配的准确率。**
- 四个原始 Qwen 反例，新事实排第一从 **1/4 变为 2/4**；城市与猫名通过，饮品和工作公司未建立正确版本链，仍失败。
- 因此 R1 全项尚未通过，不降低全局余弦阈值，不把“新版本优先”包装成“所有改口都能识别”。历史问题的具体时间点解析也不在本轮保证内。

### R2：证据充分性候选拒绝

实验室规则候选在原 216 正例中支持 216 个，原 48 个负例误报 0；但另外三个对象分离题组，各 24 正例/24 负例，均出现 **9/24 个负例误报 supported**，包括错对象和过期数值等。

它没有通过事前冻结的“负例误报为 0”门槛，**没有加入产品接口，也没有默认启用**。相关内容与所问细节存在是两回事；search 返回内容不能证明它足够作答。保留全部失败题，不事后放宽门槛。

BM25 独立候选、查询指令、真实 reranker、RRF、float32 迁移保持原默认选择；本轮没有凭推测改变生产参数。

## 5. 性能：可靠性成本必须单列

本轮运行至少五组旧/新交替配对，规模 100/1000/10000 条、64 维预计算结构向量、四线程；分别记录冷/缓存查询 p50/p95、40 次单写、20 次强化、checkpoint 和恢复。grouped 包含最终刷盘。

旧版强化仅改内存、不写 WAL。直接与它比较，新版确实多了持久化工作和耗时；这不能写成“零成本正向”或“所有维度无回退”。另测旧版每次 `save()` / 整批保存与新版 WAL / 整批 `flush()` 的同等持久确认对照，并在恢复后逐字段验证结果。

初轮随机 ID 的五组结果出现较大波动，因此保留原结果，并另外固定记录/分区 ID、`PYTHONHASHSEED=1147` 再运行五组交替复测。下表是复测五次指标的中位数，单位均为毫秒，旧 → 新；不能用它消除原始异常或忽略单组变差。

| 库规模 / 模式 | 缓存查询 p50 | 40 次写入含刷盘 | checkpoint | 恢复 |
|---|---|---|---|---|
| 100 / WAL 关 | 0.794 → 0.816 | 2.567 → 2.462 | 52.641 → 51.973 | — |
| 100 / fsync | 0.798 → 0.826 | 20.814 → 21.318 | 52.731 → 52.937 | 99.019 → 98.864 |
| 100 / grouped | 0.790 → 0.772 | 5.026 → 5.444 | 52.858 → 50.821 | 85.925 → 88.736 |
| 1000 / WAL 关 | 4.155 → 4.014 | 6.145 → 6.163 | 223.250 → 223.559 | — |
| 1000 / fsync | 4.356 → 4.142 | 26.829 → 26.220 | 337.311 → 329.228 | 608.898 → 619.416 |
| 1000 / grouped | 11.207 → 10.569 | 16.881 → 17.677 | 391.557 → 378.541 | 619.829 → 614.030 |
| 10000 / WAL 关 | 10.311 → 8.835 | 91.528 → 88.202 | 1073.766 → 996.571 | — |
| 10000 / fsync | 9.873 → 8.788 | 122.307 → 118.201 | 1007.497 → 1010.398 | 1728.456 → 1698.707 |
| 10000 / grouped | 9.687 → 10.049 | 94.192 → 75.378 | 1000.300 → 1020.415 | 1715.701 → 1706.523 |

冷查询、p95 及逐次配对详见机器证据。部分单元变好，部分变差，本轮**不验收为全面提速或所有维度严格正向**。可靠性修复的正确性已验收，性能成本在这里保留。

同等持久确认另外测五组，每组均核对恢复字段：

| 库规模 | 20 次强化，每次确认（旧 save / 新 WAL） | 20 次强化，批末确认（旧 save / 新 flush） |
|---|---|---|
| 100 | 1022.397 → 8.880 | 52.890 → 2.310 |
| 1000 | 6942.017 → 8.795 | 381.666 → 2.261 |
| 10000 | 20216.117 → 12.760 | 989.298 → 3.962 |

这六种组合各五对中新版都更快；优势来自增量提交替代全快照，不是与旧版漏写日志的路径比较。直接比较旧的内存强化路径，10000 条 fsync 下 20 次强化中位数由 0.157 毫秒增至 12.003 毫秒，明确存在成本。

字段补丁没有重写不变向量；20 次强化新增 WAL 约 10.5 KB，未随 100/1000/10000 的全库大小线性扩张。同等确认实验中，10000 条 fsync 的进程采样峰值 RSS 中位数约 416.5 → 357.9 MiB，grouped 约 412.7 → 375.2 MiB；包含解释器与分配器存量，不能当作单项操作的精确内存消耗。磁盘计数只覆盖清单与 WAL，不包含代次向量文件，不据此声称总库体积下降。
