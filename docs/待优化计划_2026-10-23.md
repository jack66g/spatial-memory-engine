# SME 待优化计划：改法、验收标准与正向收益门槛

日期：2026-10-23。状态：**待实施、待验证；本次只编写文档。**

依据：[体检报告](../lab/results/healthcheck_2026-10-23.md)、[原始证据及复现脚本](../lab/results/healthcheck_2026-10-23.json)。问题编号 B01—B10 与体检报告一致。

## 1. 我打算先做什么

先补齐跨用户隔离、删除和持久化这些可以确定对错的边界，再修接入与配置体验，最后用独立实验改进纠错排序和答案充分性判断。已能正常工作的基础读写、检索和恢复必须保住。

**“正向优化”的交付约束：修复必须有证据，既有正确行为不能回退，效果改动通过对照实验后才能采用。没有达到标准的候选方案保持未通过，不改口称为已优化。**

现在不能把尚未实施的方案保证成“任何场景都只会变好”。可以严格执行的是下面的准入条件，并把测试范围、未覆盖项和实际成本完整交给你看。

| 检查维度 | 必须满足的条件 |
|---|---|
| 正确性 | 每个已确认缺陷先有失败复现，修复后通过；隔离、删除和恢复的不变量全部成立 |
| 兼容性 | 未涉及缺陷的调用、默认开关和有效请求保持原有语义；有意改变的错误行为逐项列明 |
| 检索质量 | 冻结题集已有正确项不丢失；新题和留出集有明确收益；历史查询、否定表达和跨用户对照不退化 |
| 性能与资源 | 在相同语义、相同持久化级别下比较吞吐、p50/p95、内存和磁盘；出现可复现回退就不直接判为严格正向 |
| 数据安全 | 全部实验使用隔离库；恢复失败保留日志与错误，不能用清日志、吞异常或减少工作量换取通过 |
| 可复现与清理 | 保存源码哈希、配置、数据、逐项结果和复现步骤；清理临时进程、数据库、日志、脚本和链接 |

性能的正常波动不当作收益或回退。若修复必须增加原来漏掉的落盘工作，会同时报告“旧行为”和“完成同等持久化工作的对照”两套结果，不能通过更换对照掩盖成本。**可靠性提升但存在稳定成本时，单独列为有权衡的候选，不自动算满足你要求的纯正向优化。**

## 3. 第一阶段：隔离、删除与持久化

### B01：问答对按用户与会话配对

**拟改法：**

- 将全局唯一的待回答问题改为按 `(ns, conversation_id)` 保存；为接入层增加可选会话标识并一致透传。
- 捕获 assistant 消息时，只消费同一作用域的待回答问题。用户或会话不匹配时，不配对、不清掉别人的待回答状态。
- QA 记录、合成命中及其来源引用保留命名空间；配对前和回放前都检查作用域。
- 对旧数据中的单个 pending question 做显式兼容迁移，不猜测它属于哪个新用户或会话。

**兼容边界：**未传会话标识的旧单会话调用继续可用；多人、多会话接入要显式传递作用域。未传 ns 的查询保留既有全库语义，不能把 ns 视为身份认证。

**验收：**alice 问/bob 答、alice 问/bob 问/alice 答、同 ns 不同会话交错、并发和中途重启全部测试；跨作用域错误配对为 0，同会话正常回放继续通过。

### B02：画像与上下文使用相同的作用域

**拟改法：**

- 为上下文构造入口和画像读取入口增加显式 ns；接入层把检索使用的作用域继续传入上下文。
- 画像事实、画像快照及其缓存按作用域选择，不从全库画像直接拼接。
- 不从第一条命中推断用户身份：无命中、合成命中或多个来源时，这种推断不可靠。
- 对历史混合画像，不把包含其他用户事实的快照继续用于具名空间；能从原始引用重建时按作用域重建。

**验收：**alice 的上下文中不出现 bob 的事实或画像快照；空检索结果、画像缓存命中、关闭再开启模块、保存恢复后也成立；未分空间的旧单用户流程继续通过。

### B03：删除与派生状态在同一事务内生效

**拟改法：**

- 建立问题/答案记忆 ID 到 QA pair 的引用关系；删除任一有效来源时，清理或失效相应回放记录与向量缓存。
- 有来源引用的 QA 不能在来源被删除后，被解释为“独立 QA”继续回放；独立录入的 QA 若继续支持，必须有明确类型。
- 画像和上下文缓存同步失效。图谱等共享派生对象按来源引用处理，避免误删仍被其他有效事实支持的内容。
- 主记忆删除、QA 状态变化和必要的缓存失效纳入同一个可恢复变更单元。旧日志重放删除时也执行相同语义。
- 归档与删除分开处理：归档遵循 `include_archived`，恢复归档仍可重新使用；不把归档当永久删除。

**验收：**删除问题、删除答案、删除后立即查询、删除后重启、删除提交中断后恢复均不再回放已删除内容；其他用户及共享来源不受误伤。验证范围是当前库及后续恢复，不能据此宣称独立旧备份也已物理擦除。

### B04 + B09：补齐全部变更的 WAL，并保留原始时间

**拟改法：**

- 为引擎公开变更方法建立统一的变更收集与提交入口，覆盖 add/update/delete、强化、显式关联、融合、压缩及后台维护。
- 一个逻辑操作记录完整的实际变更：记忆字段、删除 ID、模块状态、图边及必要计数；不能只记录方法返回的第一条记忆。
- 强化记录计算后的字段结果，不在恢复时重新按当前时间计算强化；图边使用增删记录；摘要及其来源引用共同提交，恢复时不重新调用摘要生成。
- 基础 add 日志补齐原始 `created_at`、`last_hit` 和相关初始状态；重放后恢复原值，再提交快照。
- 使用变更记录或必要字段补丁，避免每次强化都复制全库或重写不变向量；沿用已有可靠的快照提交与序号水位协议。
- 明确处理序列化、追加和落盘失败：不给成功回执，不清除恢复依据，不允许未提交状态覆盖可靠快照；必要时回滚未提交变更或阻止继续使用，直到重载。

**持久化语义：**fsync 与 grouped 分开验收。grouped 保留现有异步攒批语义，不能把“进入内存缓冲”描述成“已经可靠落盘”；需要持久化确认时使用明确的 flush/提交边界。不能偷偷切换模式来美化性能。

**旧数据边界：**旧 WAL 没有记录的原始时间，不能事后精确推算。新版日志解决未来写入；旧日志按兼容方式读取，并明确其字段缺失，不伪造恢复保证。

**验收：**

1. JSON/SQLite × fsync/grouped，逐项验证强化、显式图边、融合、压缩、删除及基础时间字段。
2. 比较保存/恢复前的逻辑状态：文本、向量、时间、权重、hit_count、版本、模块引用、图边和计数；忽略随机代次文件名等非语义差异。
3. 在追加失败、恢复应用失败、快照发布失败、提交后清理前退出等位置注入故障；重复恢复不得重复强化、重复摘要或复活已删除内容。
4. 并发读写、强化、维护、保存和恢复后，作用域与状态仍一致。
5. 同时测 WAL 字节数、追加吞吐、flush、checkpoint、恢复时长和内存，不能只比较不含最终刷盘的 append 速度。

## 4. 第二阶段：过滤、批量接入与配置体验

### B05：所有召回来源执行同一套过滤规则

**拟改法：**抽出统一的候选可见性检查，向量、BM25、QA 回放和图扩展共同使用；最终返回前再校验 ns、tags、metadata、归档和策略条件。QA 合成结果继承可验证的来源字段，不能凭空补字段让它“符合过滤”。

**验收：**对各召回通道运行同一过滤矩阵；不存在的标签或元数据返回空；过滤后允许少于 top_k，不能为凑数量引入不合格结果；不带过滤的合法单用户查询保持行为。

### B06：单写、批量和官方 Client 的 ns 语义一致

**拟改法：**

- 在公共入口统一规范化命名空间，覆盖 SDK 批量的扩展开/关、WAL 开/关路径。
- REST batch 的每条记录显式解析并透传 ns；官方 `MemoryClient.add()` 增加可选 ns 参数。
- 保留现有 `metadata["ns"]` 兼容写法；同时提供显式 ns 时沿用单写接口既有的显式参数优先规则。
- 保留批量嵌入优势，不以逐条重复编码实现表面一致。

**验收：**引擎单写/批量、REST 单写/批量、MemoryClient、MCP 的写入与检索矩阵一致；显式 ns、metadata 写法、缺省及冲突输入均有用例；批量吞吐和编码次数不出现可复现回退。

### B07：MCP 正确携带 Bearer 凭据

**拟改法：**由 MCP 的 HTTP 适配层统一加请求头；凭据优先级拟定为 `SME_MCP_AUTH_TOKEN` → 兼容现有 `SME_API_AUTH_TOKEN` → 空。保持无鉴权接入可用，凭据不写入记忆、不回显到工具输出或错误日志。

401/403 给出可操作的鉴权错误；不因鉴权失败反复拉起服务，不降级关闭鉴权，不重试可能重复写入的请求。

**验收：**真正 stdio 链路覆盖正确、错误、缺失令牌及无鉴权服务；正确令牌完成 remember/recall/reinforce/stats；错误令牌失败且无写入；日志不含测试令牌明文。

### B08：上下文预算覆盖完整消息

**拟改法：**

- 对 system、当前问题、格式开销、画像、历史和检索记忆统一计数，再分配预算。
- 当前问题和必要指令优先；其余按明确优先级选择完整事实、对话轮次或可独立理解的片段，保留否定词、数值和来源。
- `reserve_profile` 作为画像预算上限，不允许画像预留挤出必需内容。
- 必需内容本身放不下时返回明确的预算错误，避免静默截断用户问题或继续发送超预算提示。
- 默认以项目的估算器执行可复现上限；如需模型级精确限制，支持显式传入对应 tokenizer，不承诺估算值等于真实模型 token 数。

**验收：**在项目估算口径下，总量不超过预算；预算不足时有明确错误；普通输入原本完全放得下时不额外删内容。覆盖中文、英文、长问题、长记忆、画像、多轮历史，以及只在句尾出现否定/数值的内容。

### B10：非法请求先校验，运行时部分成功说清楚

**拟改法：**

- 在 REST 请求层校验空白文本、metadata/tags 类型及批量条目结构，返回明确的 400/422 类错误。
- 批量请求先完成所有条目的结构校验，再开始写入；第二条结构非法时，第一条也不能先写进去。
- 嵌入或存储在执行过程中失败，与输入校验失败分开处理；若已有部分持久提交，错误回执列出已提交数量/ID及失败位置，不能模糊地让调用者整批重试。
- 保持有效请求和现有成功响应兼容；不把这次修复扩大成“批量运行过程天然全有或全无”的承诺。
- `top_k=0` 和未知 region 模式属于现有接口策略，不因探针期望不同就擅自改成破坏性校验。

**验收：**空文本和错误结构不返回内部错误；结构非法的整批请求无副作用；运行时中断的回执与实际持久状态一致；合法批量的吞吐与结果保持。

## 5. 第三阶段：纠错与检索效果，只靠实验决定采用

### R1：先保证已确认纠错链的有效版本优先

**先做确定性修复：**在相同作用域、相同事实链中，查询当前状态时有效版本优先于已失效祖先，避免仅乘一个旧事实惩罚系数后，旧版本仍排第一。查询明确的历史时间或版本时，按有效时间返回历史事实，不全局隐藏旧记忆。

**再做匹配实验：**对显式纠错，在同 ns、主体和属性的约束下改进旧事实匹配；降低对单一余弦阈值的依赖。主体、属性无法确认时保留不确定状态，不通过全局降低阈值把不同事实强行连成纠错链。

必须保护同一主体的不同属性：城市变化不能使出生地、年龄或其他未变化事实一起失效；不同用户、同名对象及否定表达都有误伤对照。

**采用条件：**

- 当前 4 个反例在“问当前状态”的条件下，新有效事实排第一；历史查询仍能找到旧事实。
- 新增至少 3 个固定种子、每个种子不少于 20 个纠错场景，并配套不少于 60 个不应被纠错的相似事实对照。
- 这些数据按对象/会话划分调试、验证、留出集；不能只换随机种子却让相同模板对象跨集泄漏。
- 留出集改善在不同种子中成立；已有正确项、误伤率、否定表达、跨语言与检索时延不退化。
- “降低旧事实排名”与“正确建立版本链”分别评分；不能靠把所有近期记录抬高掩盖匹配错误。

未通过上述条件，只保留实验结果，不修改生产默认参数。

### R2：把检索相关性与答案充分性分开

不把相似度阈值改名为答案置信度。搜索可以返回相关项目记录，但“项目相关”不足以证明里面有手机号、租金或其他具体字段。

**拟做一个可选的证据检查入口，与现有 search 分开：**

- 返回 `supported / insufficient / uncertain` 等明确状态，并给出支持片段与来源；不输出没有依据的高置信结论。
- 第一批仅针对可解释的字段和关系做规则/结构化验证，例如所问手机号、金额、时间是否在对应对象的证据中出现；同时检查否定、历史版本和对象归属。
- 不能稳定判断的问题返回 uncertain，并报告覆盖率；不能靠把全部问题都判不确定来宣称成功。
- 复杂语义验证或额外模型列为后续独立候选，先量化准确性、费用和时延，不默认增加云端调用。
- 现有搜索默认返回结构和排名保持；只有通过实验的可选能力才考虑供接入方使用。

**采用条件：**保留原 216 个可回答问题、24 个远域和 24 个近域反例；另编至少 3 组独立留出题，每组至少 24 个可回答问题和 24 个无答案问题，覆盖已知对象缺字段、错对象、否定、过期值和真正有答案的情况。

本计划拟定的验收门槛为：216 个正例中至少 195 个能给出可核查的 supported，其余只能保留 uncertain，不能错误判为确定无答案；48 个原无答案反例不误报 supported。每组留出题的正例 supported 覆盖率也至少 90%，负例误报 supported 为 0，并逐项核对支持片段是否足以回答。**这些是待达到的目标，不是现有能力声明，也不是开放世界保证。**目标在实验前冻结，未达即不采用，不能事后降低门槛。

### 本轮不默认采用的其他候选

BM25 独立召回、查询指令、真实 reranker、RRF、全局 float32 迁移都不能仅因“通常有用”就默认开启。BM25 在当前题集无额外命中；查询指令此前有得有失。它们分别做单变量实验，只有补足明确收益和兼容证据后才进入计划的交付范围。

REST 完整备份/恢复目前也有范围限制：导出含 graph，而导入入口只接收 memories。后续如补完整备份格式，应独立定义配置、模块、图和版本兼容协议，不能冒用“记忆导入成功”证明整个引擎恢复完整。

## 6. 实验怎么做，防止得到漂亮但不可靠的结论

1. **冻结对照。**保存当前工作区源码哈希、依赖版本、配置、语料、事件时间、种子和标注；包含本地未提交优化。不能 stash/reset 用户现有改动来制造基线。
2. **先复现。**把 B01—B10 转为独立、可复现的失败用例；先验证失败原因符合报告，不能把测试脚本兼容问题计作产品 bug。
3. **分批修改。**每批只改必要边界；正确性批与排序实验分开，发生回退能定位到具体变化。
4. **完整对照。**原有回归、补充探针、随机状态机、并发与故障实验共同执行；新增模块关闭时的对照，证明基础路径没有被拖坏。
5. **质量配对。**语料、向量、标注与输入顺序一致；输出逐题前后差异，分别列新增正确、丢失正确、误伤和未变化项。未经生成回答评测，不写“回答准确率”。
6. **性能配对。**相同持久化语义、线程数和硬件环境下，交替旧/新顺序，至少 5 组配对运行；冷查询、缓存查询、单写、批量、维护、恢复分开计时。显式包含 grouped 最终刷盘。
7. **规模验证。**结构与锁开销至少覆盖 100、1000、10000 条记录；真实 Qwen 查询成本另测。预计算向量的结构测试不能冒充完整模型推理性能。
8. **发布判词。**每项写清楚采用/不采用、收益、成本、回归、未覆盖项及依据。存在稳定权衡而不满足严格正向条件时，保持未验收，不能以“总体更好”掩盖。

判断普通检索是否回退时，检查原先正确且契约不应改变的样本。跨用户内容被过滤、已删除答案不再回放、非法输入不再返回 500 属于明确的预期修复差异，必须列入差异清单，不能混同为普通排序退化。
